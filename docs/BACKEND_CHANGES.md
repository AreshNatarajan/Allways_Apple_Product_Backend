# Backend Changes — Session Log

File-level changelog of backend work. For **how the app behaves** (not just what files changed), see `docs/APP_FLOW.md` — that's the one to read first in a new session. This file is the mechanical "what got touched and why" reference.

---

## Models

| File | Change |
|---|---|
| `Purchase.modal.js` | Added `vendorSnapshot`, `poType`, `reference`, `roundOff`/`roundOffAmount`, `systemInvoiceFile`, `paymentDetails[].handledBy`. Added `PURCHASE_FROZEN_FIELDS` historical-integrity freeze — enforced on `pre('save')` (including a same-`_id` multi-save collision guard), on query-level updates (`updateOne`/`updateMany`/`findOneAndUpdate`), and blanket hard-delete blocking on all delete paths. Payment fields/status/notes stay mutable always. |
| `Batch.modal.js` | Added `gstApplicable`/`purchaseGstPercent`/`saleGstPercent`. `saleGstPercent` deliberately **not** defaulted from `purchaseGstPercent` — output GST must come from `GstConfig` fresh at sale time, not a stale purchase-time snapshot (see APP_FLOW.md §4). |
| `BatchStock.model.js` | Same GST fields as `Batch`, same non-default on `saleGstPercent`, same reasoning. |
| `ProductSerial.modal.js` | Added `modelNumber`, `purchasePrice`, `sellingPrice` (all required) — every physical serialized unit is priced/modeled independently, never a shared value across a batch of serials. |
| `PendingReceive.modal.js` | Removed dead `receivedSerialNumbers[]` and embedded `receiveHistory[]` fields (confirmed write-only-never-read, 0 live documents at the time). Scoped to non-serialized lines only — serialized "pending" state is fully represented by `ProductSerial.status`. Later: added `items[].batchId`/`.batchNumber` so bulk-receive activates the batch already created at CENTRAL purchase time instead of having nothing to reference. |
| `Purchase.modal.js` | Added compound indexes (`isDeleted`+`purchaseDate`/`branchId`/`poType`/`paymentStatus`/`status`/`vendorId`, plus `items.branchId`) for the enhanced Get All Purchases filters — schema previously had none beyond the unique `purchaseNumber`. |
| `BatchStock.model.js` | Fixed a genuine correctness bug: `barcode` had a *globally* unique index, correct only when one batch could ever have one `BatchStock` row. Changed to unique per `{barcode, branchId}` so the same batch can legitimately ship to more than one branch (see CENTRAL multi-branch batch split below) — stale index dropped from the live database. |
| `StockMovement.model.js` | New — immutable, append-only ledger of every atomic stock quantity change. Discriminated by `batchId` xor `serialId`. Unique compound index prevents double-recording the same movement from the same source event. |
| `GstConfig.model.js` | New — single-document global GST rate settings. Not seeded, nothing reads it yet (deferred to the Sale phase). |
| `ReceiveHistory.modal.js` | Append-only guards added (update/delete blocked on all realistic Mongoose paths). Converted to Mongoose-9 promise-style hooks (see note below). |
| `TransferHistory.modal.js` | Same append-only guards + Mongoose-9 fix. |
| `Sale.modal.js` | Added `customerSnapshot`, flat per-line batch fields (`batchId`/`batchNumber`/`barcode`/`purchaseId`/`purchaseNumber` — legacy `batches[]` kept for old documents), `SALE_FROZEN_FIELDS` freeze guard (same pattern as Purchase, document + query level). Later: `paymentStatus` enum changed from `["PAID", "PENDING", "PARTIAL"]`/default `"PENDING"` to `["PAID", "PARTIAL", "UNPAID"]`/default `"UNPAID"` — safe as a real rename (not just a display label, unlike Purchase's `PENDING`) since no Sale frontend exists yet to depend on the old value. See `createSale.controller.js` below. |
| `StockTransfer.modal.js` | Deleted — confirmed dead (0 documents, 0 references anywhere) both before and after removal. |
| `Product.modal.js` | `modelNumbers` (array, required non-empty for serialized) → `modelNumber` (single string) — "one serialized product = one model number." A migration script backfilled `modelNumber = modelNumbers[0]` for every existing serialized product before the array field was dropped. |
| `ProductSerial.modal.js` | Added `purchaseGstAmount`, `hsnCode` (neither existed before — HSN lived only on the live `Product` document). Together with the now-real `purchaseGstPercent` (see `createPurchase.controller.js` below), `ProductSerial` is now the actual source of truth for a physical unit's purchase-time GST, permanently. |
| `GstConfig.model.js` | Expanded from 2 fields (`marginSchemeRate`/`standardRate`) to a full settings surface: `companyGstNumber`, `companyDetails` (name/address/phone/email), `availableGstRates` (array), `invoiceSettings` (prefix/footer/terms). Still a singleton, still auto-created (not seeded) on first read via the new `getOrCreateGstConfig()` service. |
| `Sale.modal.js` | Indexes replaced with `isDeleted`-leading compounds, matching `Purchase.modal.js`'s proven convention (`isDeleted+saleDate/branchId/customerId/paymentStatus/status`). A pre-existing redundant `saleNumber` index (duplicating the field-level `unique: true`, causing a Mongoose duplicate-index warning) was removed while there. |

**Mongoose 9 note:** this project runs Mongoose 9.7.4, which removed callback-style (`next`) middleware entirely. Every hook across every model above is promise-style (`function () { ...; throw err; }`, no `next` parameter) — mixing styles throws `TypeError: next is not a function` at runtime. Caught via live functional testing, not static checks.

## Controllers / Services

| File | Change |
|---|---|
| `controllers/purchase/createPurchase.controller.js` | Major rework across several passes: `vendorSnapshot` populated + vendor validated existing/active; `handledBy` stamped from `req.user` on every payment; server-computed `roundOffAmount`; global (not per-branch) batch numbering; GST fields stamped on `Batch`/`BatchStock`/`ProductSerial`; a `StockMovement` written for every direct-receive batch/serial; serialized items restructured to one-item-per-physical-unit (`serialNumber` + `modelNumber` per item, not a shared `serialNumbers[]` array); HSN sourced from `Product.hsnCode` for **both** serialized and non-serialized (never client-supplied, rejects 400 if the product has none); item-level `branchId` bug fixed (was hardcoded `null` for non-SUPER_ADMIN); system invoice generated post-commit, uploaded to S3, enriched in-memory with `modelNumber`/`description`/branch address before rendering. Later: for CENTRAL non-serialized items, groups lines by product+cost-basis and creates one `Batch` per group immediately (barcode ready before goods ship), instead of no batch existing until receive time; `PendingReceive` rows now carry that batch's `batchId`/`batchNumber`. |
| `controllers/purchase/getPurchaseById.controller.js` | Invalid-id now `400` (was falling through to a `500`); fixed serial-to-item cross-contamination (was grouping all serials of a product onto every item of that product instead of matching each item's own exact serial number); added `modelNumber` to the response (previously missing entirely); added a bulk `Branch` lookup so item-level branch assignment is reliable even before anything's been received; `paymentDetails[].handledBy.userId` now populated. |

Removed the write entirely rather than patch around it — it was redundant with `PendingReceive`/`ProductSerial`, which already track this and are what `getPurchaseById` actually reads. |

Items table columns fixed regardless of product type: Product Name, Model, Serial Number, Description, Qty, HSN/SAC, GST%, GST Amount, Total Amount. No longer writes to local disk — returns an in-memory buffer only. |

**Why the upload fixes mattered beyond "not using S3":** this app mounts `express-fileupload` globally in `server.js`. A second `multer` parser on the same request always fails ("Unexpected end of form") because the multipart stream is already consumed. Both `/purchase/upload-invoice` and `/purchase/upload-payment` were **silently non-functional in production**, not just off-convention — found via live testing, not assumed. `/purchase/upload-signature` still has this exact bug and was **not** fixed (unused by the current Purchase Create frontend, flagged not silently left looking "already handled").

## Known open items

- `Batch`/`BatchStock` have no historical-integrity freeze (unlike `Purchase`/`Sale`) — recommended hardening, not urgent, nothing broken today.
- `Inventory` is now redundant with `BatchStock` for the CENTRAL receive path (kept as a dual-write for backward compatibility) — candidate for removal once confirmed nothing else still reads it.
- Transfer is not yet migrated to the `StockMovement`/`BatchStock` architecture — still legacy. Bulk-receive and Sale **are** migrated now (see §9/§12 in `APP_FLOW.md`).
- **Resolved**: `Sale`'s margin-scheme GST now reads `GstConfig.marginSchemeRate` live at sale time — see §17 in `APP_FLOW.md`. `ProductSerial.saleGstPercent`/`Batch.saleGstPercent`/`BatchStock.saleGstPercent` are now vestigial (left in place, nothing reads them anymore) rather than removed, avoiding unnecessary schema churn.
- **Resolved**: Sale Create and Sale Detail frontend screens both now exist — see §14/§16 in `APP_FLOW.md`.
- `Sale.customerSnapshot` is never actually populated by `createSale.controller.js` — confirmed via live data (always empty even on a sale with a real linked customer). Doesn't block anything today (live `customerId` population covers display), but means Get All Sales' `customerStats.topCustomers` currently shows "Unknown Customer." Found during Get All Sales testing, not fixed (out of scope for that task).
- Purchase Create's frontend doesn't yet send `item.purchaseGstPercent` for serialized items, even though the backend can now accept and store a real value (see §17 in `APP_FLOW.md`) — a frontend follow-up task, not started.
- A latent edge case in `createPurchase.controller.js`/`getAllPurchases.controller.js`: if one purchase has two separate item lines for the *same* product going to the *same* single branch (rather than one combined line), batch-matching by `productId`+`branchId` alone can attach the same batch to both lines instead of their own. Only affects that narrow duplicate-line case — genuinely different branches (the multi-branch split feature) are unaffected and verified correct. Not fixed yet, flagged during Purchase Detail Page frontend work.
- **AWS access key quarantined as compromised by AWS itself** — see `docs/APP_FLOW.md` §7. Needs rotation outside this codebase; not something this session could fix.
